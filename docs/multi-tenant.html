Multi-tenant setup

Run Sentinel Concierge for more than one business on a single concierge-service deployment.

How a message is matched to a business

Both WhatsApp and Twilio can route more than one of a business's own numbers to the same webhook URL — WhatsApp's payload carries the receiving number as metadata.phone_number_id, Twilio's as the To field. channel-whatsapp and channel-sms surface that value as NormalizedMessage.businessChannelId, and concierge-service resolves which BusinessConfig applies per-message by looking it up.

Telegram has no equivalent: a bot's identity is implicit in its webhook URL/token, not present in the update payload. Serving multiple Telegram bots from one deployment isn't covered by this mechanism — it would need separate bot configs mounted at separate routes.

Single-tenant mode (default)

Set BUSINESS_CONFIG_PATH to one JSON file. Every inbound message resolves to that same business, regardless of businessChannelId — this is unchanged from before multi-tenancy existed.

BUSINESS_CONFIG_PATH=./_internal-docs/data/business-config.example.json

Multi-tenant mode

Set BUSINESS_CONFIGS_DIR instead — a directory containing one JSON file per business, each named <businessChannelId>.json. It takes precedence over BUSINESS_CONFIG_PATH if both are set.

BUSINESS_CONFIGS_DIR=./business-configs

Example layout:

business-configs/
├── 1234567890.json          # keyed by a WhatsApp phone_number_id
├── +18885550000.json        # keyed by a Twilio "To" number
└── faq-blueprints/
    ├── business-a.json
    └── business-b.json
The directory listing is not recursive — every top-level *.json file is read as a BusinessConfig. Each business's FAQ blueprint must therefore live in a nested subdirectory (e.g. ./faq-blueprints/business-a.json, referenced by that business's own faqBlueprintPath) rather than directly inside BUSINESS_CONFIGS_DIR — otherwise it would itself be misread as a malformed business config and fail validation at startup.

Example: 1234567890.json

{
  "businessId": "business-a",
  "timezone": "Asia/Singapore",
  "faqBlueprintPath": "./faq-blueprints/business-a.json",
  "calendarId": "business-a-calendar-id",
  "businessHours": { "...": "..." }
}

What's shared vs. per-business

ResourceScopeWhy
AI provider (OpenAI/Gemini)Shared across all tenantsStateless per-request API calls — no reason to duplicate
Google Calendar clientShared connection, per-business calendarIdOne service-account credential can hold access to every business's calendar; only the calendar id and business hours differ per tenant
Business hours, FAQ knowledge basePer-businessEach business's own content
Session statePer-businessSession ids are scoped by tenant — the same customer messaging two different businesses never shares conversation state

Unrecognized businessChannelId

If an inbound message's businessChannelId doesn't match any configured business, the service replies with a safe fallback message rather than crashing or silently routing to the wrong tenant's configuration:

"Sorry, this number isn't set up with us yet. Please contact the business directly."
