Data contracts

Every interface below lives in @gracesoft-sentinel/core and is defined with Zod — the schema is the type, and every implementation is checked against a shared contract test suite so behavior stays consistent regardless of which channel/provider is plugged in.

NormalizedMessage

What every ChannelAdapter.parseInbound() produces from a channel's raw webhook payload. Agents only ever see this shape — never WhatsApp/Telegram/Twilio's own payload structure.

{
  id: string;
  channel: string;                 // "whatsapp" | "telegram" | "sms" | ...
  senderId: string;                // the chatter's own id on that channel
  timestamp: string;               // ISO 8601
  text?: string;
  media?: {
    type: "image" | "audio" | "video" | "document";
    url?: string;                  // always a data: URI once resolved — see note below
    mimeType?: string;
    caption?: string;
  }[];
  quickReplyId?: string;           // id of a button/list item the sender tapped, if any
  businessChannelId?: string;      // which of the *business's* channel identities received this
  raw: unknown;                    // untouched source payload, for edge cases/debugging
}
Media urls are always resolved server-side into a base64 data: URI before an agent sees them — never a bare channel CDN link. WhatsApp/Telegram/Twilio media URLs need an auth header or token to fetch, which shouldn't leak to a third-party AI provider's own outbound fetch.

businessChannelId carries the WhatsApp phone_number_id or Twilio To number a message arrived on — the mechanism a single deployment uses to tell tenants apart. See Multi-tenant setup. It's undefined on Telegram, whose bot identity lives in its webhook URL/token rather than the update payload.

NormalizedResponse

What an agent returns, translated back into a channel-specific payload by ChannelAdapter.formatOutbound().

{
  text?: string;
  quickReplies?: { id: string; label: string }[];
  media?: NormalizedMedia[];
  meta?: Record<string, unknown>;  // channel-specific extensions that don't warrant a core field
}

Channels with no native interactive UI (SMS) degrade quickReplies to a numbered plain-text list; the agent's own free-text selection fallback resolves a typed number back to the intended choice.

ConversationState

The session shape persisted between messages (Redis-backed by default). context is an intentionally open bag — each agent owns the shape of its own in-progress state without core needing to know about it.

{
  sessionId: string;
  channel: string;
  userId: string;
  agent: string;
  createdAt: string;   // ISO 8601
  updatedAt: string;
  context: Record<string, unknown>;
}

Session ids are scoped by tenant, channel, and sender (concierge:<tenant>:<channel>:<senderId>) so the same person messaging two different businesses — or the same business over two different channels — never shares state across them.

BusinessConfig

One config shape both agents consume, resolved by the service layer per business.

{
  businessId: string;
  timezone: string;              // IANA, e.g. "Asia/Singapore"
  faqBlueprintPath: string;      // path to this business's FAQ grounding content
  calendarId: string;            // Google Calendar id
  businessHours: {
    timezone: string;
    weekly: {                    // mon..sun, null = closed that day
      mon: { open: string; close: string } | null;
      // ... tue..sun
    };
    exceptions: {                 // dated overrides — public holidays etc.
      date: string;               // "YYYY-MM-DD"
      hours: { open: string; close: string } | null;  // null = closed all day
      reason?: string;
    }[];
  };
}

Provider interfaces

These are what an agent depends on instead of a concrete SDK — agent-concierge/agent-cook never import OpenAI, Google, or any channel package directly (enforced by a static boundary check, not just convention).

ChannelAdapter

interface ChannelAdapter {
  channel: string;
  parseInbound(payload: unknown): Promise<NormalizedMessage>;
  formatOutbound(response: NormalizedResponse, context: { recipientId: string }): unknown;
}

Implemented by channel-whatsapp, channel-telegram, channel-sms.

AIProvider

interface AIProvider {
  chatComplete(input: { messages: {role, content}[]; temperature?; maxTokens? }): Promise<{ text: string }>;
  visionAnalyze(input: { image: {url} | {base64, mimeType}; prompt? }): Promise<{ text: string }>;
  embed(input: { input: string | string[] }): Promise<{ vectors: number[][] }>;
  transcribeAudio(input: { audio: {url} | {base64, mimeType}; language? }): Promise<{ text: string }>;
}

Implemented by provider-ai-openai (chat/vision via GPT models, transcription via Whisper) and provider-ai-gemini. embed is why Gemini was chosen as the second provider over Anthropic — Anthropic has no native embeddings API, and every implementation must satisfy the full interface.

CalendarProvider

interface CalendarProvider {
  getAvailability(input: { calendarId, from, to, timezone }): Promise<{ start: string; end: string }[]>;
  createBooking(input: { calendarId, start, end, timezone, summary, attendee? }): Promise<{ id, start, end }>;
  getBusinessHours(input: { calendarId }): Promise<BusinessHours>;
}

Implemented by provider-calendar-google (Google Calendar).

SessionStore

interface SessionStore {
  get(sessionId: string): Promise<ConversationState | null>;
  set(state: ConversationState, ttlSeconds?: number): Promise<void>;
  delete(sessionId: string): Promise<void>;
}

Implemented by provider-session-redis.

RecipeSourceProvider

interface RecipeSourceProvider {
  findRecipes(input: { query: string }): Promise<{ id: string; title: string; raw?: unknown }[]>;
}

Implemented by provider-drive-google — retrieves a personal recipe from a Google Drive folder via embeddings-based semantic search (RAG) rather than AI generation. Optional: agent-cook only takes this path when a provider is actually configured (GOOGLE_DRIVE_RECIPES_FOLDER_ID), and the matched document's content is returned verbatim — it's the user's own free text, not a structured recipe.
